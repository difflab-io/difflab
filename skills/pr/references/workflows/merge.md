# Merge and observe base-branch CI

Resolve the explicit PR/MR or unique open one for the current branch. Check its repository, URL, head, actual base, draft state, mergeability, required checks, permissions, and allowed merge methods. Stop for a draft, conflict, denied merge, or unmet protected-branch rule; never bypass a required check. Warn if local commits are not in the remote head; do not silently push them. Select the requested merge method, or the repository's allowed default. For squash onto a release branch, check the repository's release policy and commit subject rather than imposing a universal convention. Show the exact target, method, potential branch deletion, and CI implications; obtain confirmation before merging. Branch deletion is separate and requires an explicit request.

After the forge reports success, verify the actual merged state, base branch, and resulting base SHA. A squash or rebase merge need not preserve the head SHA. Watch only CI triggered on that base branch for the resulting base SHA, using the [provider's](../providers/index.md) existing run or pipeline metadata. Do not mistake an older base run, pull-request validation, merged-results preview, or an unrelated workflow for post-merge CI. Allow a bounded wait for new runs to appear and for relevant checks to finish; if none appear by the wait limit, distinguish no CI configured from delayed, skipped, or unknown CI and report what could be verified. Report green only when relevant runs conclude successfully. For failed or canceled checks, provide names, URLs and useful failure-log excerpts. For a timed-out watch, report the pending checks and link. The merge remains completed even if observation fails.

With `--autofix`, only after confirming a failing post-merge base-SHA run, diagnose its logs and relevant code, propose the minimal fix, and check authorization to modify the base branch. Protected or permission-restricted base branches require a separately authorized follow-up branch/PR; stop instead of bypassing protection, force-pushing, or claiming an automatic repair. Stop for ambiguous ownership, unsafe local state, unrelated failures, or uncertain diagnosis and ask before modifying anything. If authorized, apply one focused fix, run relevant local checks, then commit and push only the agreed fix through normal repository policy. Watch new base-SHA CI after that push. Count each diagnose-fix-verify attempt as one round; never exceed five rounds, including failed local verification rounds. A green recheck ends the loop; exhausted rounds, no matching CI, or a new blocker stops it. Never imply that a failed attempt or completed merge has been rolled back.

Report the merge URL and base SHA, method, CI run identity and outcome, failed checks/log links, each attempted fix and verification result, and the number of autofix rounds used. Make post-merge failure prominent even if merge succeeded. Do not delete local branches, switch worktrees, or clean up remotes without a distinct explicit request.
