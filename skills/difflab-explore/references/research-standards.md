# Research standards

- Start with the question, constraints, codebase context, and prior art: inspect comparable code already in this repository and analogous open-source implementations. Survey the existing library/tool ecosystem before proposing custom work. Do not assume a library or API exists because you recall it.
- Fetch and actually read primary sources (official documentation, source code, changelogs, package metadata, licensing files, reference implementations). Cite direct URLs inline beside each material claim, plus access date and version, release or commit when relevant. Search snippets or unsourced summaries are leads, not citations. Check that links support the exact claim, including API signatures and integration details. If a source cannot be fetched, mark the claim unverified or omit it.
- For candidate libraries, verify maintenance signals (recent releases/commits, issue activity when relevant), license and compatibility with this project; distinguish verified observations from interpretation. Do not invent benchmarks, capabilities, or license terms. If comparisons depend on outdated releases, say so.
- Mark **Fact**, **Inference**, and **Unknown** distinctly, especially for trade-offs and recommendations. Record conflicting sources and uncertainties, evidence freshness, and what evidence would resolve them. A revisit must distinguish new evidence from old evidence rather than presenting old notes as newly verified.
- Research notes cover the question, existing approaches, findings, trade-offs and fetched sources. The summary links the notes and names distinct options without assuming one is best. Only create proposal documents when requested; proposals should have concrete integration boundaries, comparative costs, and supporting citations, not implementation code or task lists. A proposal is not an ADR or implementation commitment.
- Use Mermaid code fences for diagrams when a relationship or data flow is clearer visually; do not add ornamental diagrams or ASCII flowcharts. Keep prose paragraphs unwrapped (one paragraph per line) and use explicit headings and concise language.
- Delegate only genuinely independent research angles when effort warrants it: light effort/tier for narrow source collection, standard for codebase and ecosystem comparison, heavy for complex synthesis. Specify question, output file, sources to fetch, and an evidence/unknowns handoff. Choose parallel tasks by independent angle, not by a fixed number of agents. No named agent files, provider-specific models, or scripts are required. Verify delegated citations and conclusions before publishing.
