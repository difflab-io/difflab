# Research standards

- Define the question and constraints. If the question concerns this repository, inspect its relevant code and prior work. For general research, skip the codebase scan. Check comparable open-source work and existing libraries before proposing custom code.
- Read primary sources: official docs, source, changelogs, package metadata, and licenses. Cite direct URLs beside claims. Add the access date and relevant version or commit. Search snippets are leads, not evidence. If you cannot read a source, mark its claim unverified or omit it.
- For each library, check maintenance, license, and compatibility when relevant. Do not invent APIs, measurements, or terms. Mark facts, inferences, and unknowns. Note conflicting or old evidence.
- Link research notes from the summary. Name distinct options without forcing a recommendation. Write proposals only when requested. A proposal gives boundaries, costs, and evidence; it is not an implementation plan or ADR.
- Use Mermaid only when a diagram explains a relationship. Keep paragraphs on one line. Use short headings and sentences.
- Delegate independent research when useful. Choose a light tier for source collection, standard for comparisons, and heavy for difficult synthesis. Give each worker a question, output path, and source requirements. Verify its claims before publishing. Do not require named agents or provider-specific models.
