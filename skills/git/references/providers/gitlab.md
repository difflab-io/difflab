# GitLab context for Git workflows

Confirm that the selected origin or explicitly named remote belongs to GitLab and that the authenticated account can read the project and update the selected branch. Inspect the project default branch, actual remote tracking refs, and any matching merge request's source and target. GitLab's authenticated CLI or API may supply MR base/head metadata and pipeline/job results; use current official GitLab documentation to check unfamiliar permissions or interfaces. This reference stands alone and does not depend on another skill.

A matching MR's target can inform a squash or rebase base, but first verify that its source project and branch match this checkout; fork MRs may have a different push destination. Branch protection and permissions can prohibit any push even if local history was changed. For an explicitly authorized rewrite, use a lease-protected update only to the verified feature branch, never the default or protected branch. If the lease is rejected, inspect concurrent changes and stop; do not replace them.

After an explicitly requested successful push, identify the pipeline for the exact pushed SHA and ref in the correct project; do not mistake an MR pipeline, detached pipeline, or prior branch pipeline for the new branch run. Some projects have no pipeline for this event. Wait a bounded time for creation and completion, report pending or absent pipelines distinctly, and give failing job names and available trace or pipeline URLs for failures. If access or visibility is missing, say CI is unverified rather than claiming green. Local-only actions need no forge API access beyond the authorized remote fetch.
