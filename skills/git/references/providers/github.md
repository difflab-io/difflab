# GitHub context for Git workflows

Confirm that the selected origin or explicitly named remote belongs to GitHub and that the authenticated account has access to the repository and branch. Inspect the configured upstream and default branch rather than assuming their names. Use existing Git capabilities for local history and branch updates; GitHub's authenticated CLI or API may supply PR base/head metadata and CI results. Check current official GitHub documentation when an interface or permission is unclear. Do not require another skill or install a tool as an implicit side effect.

For a branch with an open PR, use its actual base branch for squash or rebase when the user has not supplied a base. Do not treat a PR identifier from another repository as permission to rewrite the current branch. Before any remote write, verify branch permissions and compare the remote tip with the previously observed tip. Rewritten feature history requires a lease-protected update; protected/default branches must not be rewritten. A rejected lease is evidence of concurrent work, not a reason to override it.

After an explicitly requested successful push, identify workflow runs or checks by the pushed commit SHA, repository, branch, and event; a similarly named older run is not proof of success. Allow for CI startup delay, use a bounded wait and distinguish an absent run from a pending or skipped one. Report completed status and failing checks with run URLs or available failure logs; never call an unseen run green. If authentication, CI visibility, or permissions are insufficient, report that limit and the pushed state separately. The local-only paths do not require GitHub access beyond fetching the authorized remote.
