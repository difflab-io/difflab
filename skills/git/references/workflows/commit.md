# Commit

Create a professional conventional commit from the intended changes. The default is **local-only**. Only `--push` or an explicit request to push authorizes a remote update. Never push as a side effect of a commit request.

1. Inspect the current branch, index, worktree, and intended diff. Respect staged selections; do not stage unrelated or untracked files indiscriminately. Ask which changes to include when the scope is ambiguous. Check for secrets, credentials, generated artifacts, and accidental deletions before staging; stop on suspected secrets. Check repository-specific contribution rules and configured format, lint, and test checks. Run appropriate checks before committing; report any failures and stop rather than silently bypassing them.
2. Propose a conventional subject with an imperative summary, no final period, and at most 72 characters. Use `feat` for functionality, `fix` for corrections, `refactor` for structural changes, `docs` for documentation, `test` for tests, and `chore` for maintenance; use a short scope when a subsystem is clear. Keep the optional body short, in bullets about the change and its reason. Only mark a breaking change with a `!` subject or `BREAKING CHANGE` footer when the user explicitly authorizes the major-version signal; otherwise describe the change without that marker. Do not promise a version bump without checking the release configuration.
3. Show the proposed message and file set and get confirmation unless the user already supplied and approved the exact message and scope. If independent logical changes warrant separate commits, propose the grouping and confirm each group; ensure no changes are omitted or mixed across groups. Preserve genuine human coauthor trailers. Do not add agent self-attribution in the subject, body, or trailers, including follow-up commits. Do not install or require a commit-message hook.
4. Commit the reviewed staged changes locally. Check the resulting status and commit identity; report anything left uncommitted. If `--push` was requested, verify the destination remote, upstream and branch permissions first, then use a normal, non-forced push of only this branch. Do not push a protected branch or create an upstream without confirming an ambiguous destination. If the push fails, report the reason; never replace it with a force push.
5. After a successful push, use [GitHub](../providers/github.md) or [GitLab](../providers/gitlab.md) guidance to identify CI for the pushed branch and commit. Watch an identifiable run to completion within a bounded wait, then report green, red with failing checks and logs, pending/timeout, or no CI separately. Do not silently create fix commits or claim success when a run was not found. A CI failure does not undo the push; ask before attempting repairs.
