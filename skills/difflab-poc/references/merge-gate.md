# Required merge gate

Before `poc init` or `poc new`, identify the actual remote forge and every protected production target (at least `main`). A merge gate must reject a pull/merge request with source branch `poc/*` while permitting that branch to be created and pushed. Prefer a forge-native source-branch restriction **if the forge really exposes one**. A rule restricting the name or creation of the PoC branch, a rule protecting only the destination from direct pushes, or an optional CI workflow does not meet this requirement.

For GitHub, current branch rulesets target destination refs rather than source-branch patterns. The fallback in this repository is `.github/workflows/on-poc-merge.yml`, whose check is `Block PoC source branch` in job `block-poc-source`. The workflow runs on `pull_request_target` from the trusted base branch and evaluates `github.event.pull_request.head.ref` (including fork PRs). It must never check out or run code from the PR, request secrets, or gain write permissions; a PoC branch must not be able to edit its own guard. Test that the required check actually binds to and blocks a PoC PR before claiming full protection. It must be present on the target's default/base branch and its check must be **required** by an active ruleset or branch protection rule on each production target. Check effective rules through the authenticated forge API, not just local YAML; verify the rule applies to the intended target and has no relevant bypass actor. A failing test PR from a disposable `poc/*` head is stronger evidence when authorized. Do not assume an administrator cannot bypass repository policy.

For GitLab or other forges, check whether a native merge restriction inspects source branch name. If not, require an enforced source-aware MR status/pipeline or equivalent protected-target check and verify that a blocked or missing check actually prevents merging. Never claim the GitHub workflow protects GitLab. If enforcement cannot be inspected (permissions/tier/API limitation), **stop** rather than inferring safety.

If the gate is absent, tell the user exactly what remote rule/check is needed and ask permission to configure it. Remote policy mutation is a separate approval. After approval, install/enable the rule as appropriate, verify it is effective, and only then rerun init/new; do not continue from an unverified assumption. A locally added workflow does not become active on GitHub merely because it exists in a worktree. If a new required check would block the PR that installs its trusted `pull_request_target` workflow, create the remote ruleset in evaluation mode first. After the workflow lands on the default branch, switch the rule to active, inspect effective rules, and exercise an authorized disposable `poc/*` PR before claiming enforcement. An evaluation-only rule does not satisfy the gate.

References: [GitHub available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets), [GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [GitLab merge settings](https://docs.gitlab.com/user/project/merge_requests/).
