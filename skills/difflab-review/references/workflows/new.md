# Review new

1. Confirm the repository root, initialized `.difflab` store, current branch, and an actual diff. Do not review an empty or unrelated diff. With `--bg`, delegate this workflow to a native background subagent with the exact target; for remote mode grant permission to commit, push, create a draft PR, and post inline findings, while `--local` grants no remote or commit rights. Return control immediately. The worker never asks mid-run for permissions: on ambiguity, failed checks, or unavailable forge access it stops and reports a blocker. If no native background capability exists, report that instead of faking it.
2. Select the target deterministically: an explicit plan or issue, then a unique matching plan, issue, or branch. A focus such as “security” directs the review; it is not the artifact slug. In foreground, ask if several targets match or a review directory collides. In `--bg`, stop and report the ambiguity rather than asking or overwriting. Use `YYMMDD-{slug}`.
3. Call `scaffold({name:"code-review",cwd:<absolute repository root>,path:".difflab/reviews/YYMMDD-{slug}",filename:"REVIEW.md"})`. Read the resulting file and fill every applicable section without removing headings or human-authored text. Record the diff/commit, intent, reviewer, checks, and skipped checks. Apply focus to review depth, not to inventing findings.
4. For `--local`, add findings as generated entries under `## Change Requests` in `REVIEW.md`. Do not create a PR or make any remote write.
5. For remote review, check authenticated `gh` or `glab` access and verify the intended change set with format, lint, and tests. Inspect staged and untracked paths for secrets and unrelated files; stage only the intended source/config changes, not `.difflab` project-store artifacts. If there are uncommitted changes, create a conventional commit without agent self-attribution and push the branch. If a commit, push, or check fails, stop before creating a PR or posting findings. Never force-push merely to start a review.
6. Reuse a suitable existing PR; otherwise scaffold `pull-request-description` to a distinct non-overwriting file in the review directory (for example `PR-DRAFT.md`), fill every `{{...}}` placeholder, and open a draft PR from the pushed branch with that file as its body. Re-read the actual PR diff after pushing; do not anchor comments to stale working-tree lines. Use the forge CLI's authenticated API where needed to anchor findings to changed lines as inline change requests on the PR, not an overall comment. In foreground, stage comments in a pending review where supported; otherwise get explicit confirmation before posting public inline comments. In `--bg`, post verified inline comments without prompting (submit a pending review without an overall body when needed). If the forge cannot publish inline-only comments, stop and report a blocker rather than posting an overall comment. Never post a finding against an unmapped or outdated diff line.
7. Every generated finding/comment must end with `> Generated via <actual model name>`. Keep human comments verbatim. If the model name is unavailable, stop before posting comments; do not guess.
8. Report the exact REVIEW.md path, commit SHA, PR identity, findings, checks, skipped checks, and any forge/authentication failure. Do not approve or merge as part of `new`. Keep foreground pending review comments unpublished where supported; `--bg` publishes verified inline findings so the PR actually carries its review comments. If there are no findings, do not invent any.
