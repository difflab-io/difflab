# Review new

1. Confirm the repository root, initialized `.difflab` store, current branch, and an actual diff. Do not review an empty or unrelated diff.
2. Select the target deterministically: an explicit plan or issue, then a unique matching plan, issue, or branch. A focus such as “security” directs the review; it is not the artifact slug. Ask if several targets match. Use `YYMMDD-{slug}` and ask before colliding with an existing review directory.
3. Call `scaffold({name:"code-review",cwd:<absolute repository root>,path:".difflab/reviews/YYMMDD-{slug}",filename:"REVIEW.md"})`. Read the resulting file and fill every applicable section without removing headings or human-authored text. Record the diff/commit, intent, reviewer, checks, and skipped checks. Apply focus to review depth, not to inventing findings.
4. For `--local`, add findings as generated entries under `## Change Requests` in `REVIEW.md`. Do not create a PR or make any remote write.
5. For remote review, check authenticated `gh` or `glab` access and verify the intended change set with format, lint, and tests. Inspect staged and untracked paths for secrets and unrelated files; stage only the intended source/config changes, not `.difflab` project-store artifacts. If there are uncommitted changes, create a conventional commit without agent self-attribution and push the branch. If a commit, push, or check fails, stop before creating a PR or posting findings. Never force-push merely to start a review.
6. Reuse a suitable existing PR; otherwise scaffold `pull-request-description` to a distinct non-overwriting file in the review directory (for example `PR-DRAFT.md`), fill every `{{...}}` placeholder, and open a draft PR from the pushed branch with that file as its body. Re-read the actual PR diff after pushing; do not anchor comments to stale working-tree lines. Use the forge CLI's authenticated API where needed to anchor findings to changed lines as inline change requests on the PR, not an overall comment. When the forge supports pending review drafts, stage comments there; otherwise get explicit confirmation before posting public inline comments. Never post a finding against an unmapped or outdated diff line.
7. Every generated finding/comment must end with `> Generated via <actual model name>`. Keep human comments verbatim. If the model name is unavailable, stop before posting comments; do not guess.
8. Report the exact REVIEW.md path, commit SHA, PR identity, findings, checks, skipped checks, and any forge/authentication failure. Do not approve or merge as part of `new`. Keep pending review comments unpublished where supported.
