# `adr new`

Author a decision from user-provided context and evidence. This is not an implementation task.

1. Confirm the repository and read the index, local template, and both numbered layouts: `adr/NNNN-kebab-title/ADR.md` and legacy `adr/NNNN-kebab-title.md`. Check numbered directories without ADR.md too; never replace or discard their resources. Treat an explicit short name after `new` as the intended slug (for example, `adr new auth` or `adr new auth: <decision context>`); prefer a supplied path/number, then that name, then a unique matching decision topic. Treat a multiword natural-language request without a `name:` separator as decision context, not as a first-word name. Do not silently replace a supplied name with an inferred title. If a number resolves to multiple paths, or multiple records match, ask which one; if a matching authored ADR exists, ask whether `adr update` was intended. Reuse a clearly matching, still-placeholder scaffold (including a legacy flat scaffold) rather than allocating another number. An empty/reserved directory is not an ADR scaffold: ask before recovering it. Never overwrite an existing record by scaffolding.
2. Ask for the problem, decision authority, plausible options, constraints, trade-offs, and supporting evidence if they cannot be established from the request or linked material. With a name alone (`adr new auth`), retain `auth` as the intended slug and ask for the missing decision context before creating or filling a record. An explicit chosen option is required to state an outcome. If research is insufficient, explain the gap and offer `explore new` as a separate step; do not fabricate measurements, participants, citations, or an accepted status. A proposed outcome may be a recommendation awaiting approval; label it as such.
3. If no matching scaffold exists, follow the numbering and exclusive directory reservation from `init.md`, then call MCP `scaffold({name:"architecture-decision-record",cwd:<absolute repository root>,path:"adr/NNNN-kebab-title",filename:"ADR.md"})`. Read the resulting file before editing it. If reservation or scaffolding fails, do not create an index entry. If an existing scaffold has customized headings, retain them. Never migrate an existing legacy flat ADR as part of authoring.
4. Fill placeholders in the record with short, concrete sentences. Preserve core MADR sections: Context and Problem Statement, Decision Drivers, Considered Options, Decision Outcome, Positive and Negative Consequences. Compare options against drivers and explain why the selected option wins. Keep the template's status/date/deciders formatting, using `proposed` unless the user supplies evidence of approval. Omit optional example sections or empty appendices instead of leaving unfilled placeholders. Add links to relevant local evidence or authoritative external sources, with dates/versions when relevant; identify inference and open questions. Add a small Mermaid diagram only when it clarifies boundaries, data flow, or alternatives; put supporting static resources beside `ADR.md` and link to them relatively (for example, `./topology.svg`).
5. Update `adr/README.md` only after the ADR is authored. Preserve its introduction and references. Replace the `No ADRs yet.` row when adding the first record; otherwise insert a linked `ADR-NNNN` row in numeric order under `ADR | Status | Summary`. Use the relative link `(NNNN-kebab-title/ADR.md)` for new directory records, or `(NNNN-kebab-title.md)` for a reused legacy scaffold, the record's exact status, and a one-line factual summary. If its number is already indexed and the link points to the same record, correct that row instead of adding a duplicate; if it points elsewhere, stop and ask. If the index is inconsistent or its format differs, stop and ask before rewriting it; do not delete other rows.
6. Check that links resolve, no placeholders remain in the authored record, and the status/index agree. Report the record and index paths; do not commit or apply the architecture.

Example: “adr new queue ownership: choose one consumer per partition based on our load-test report” fills a matching draft or scaffolds the next number first. “adr new database” without decision context should prompt for details, not produce a made-up decision.
