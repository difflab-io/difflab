# `adr update`

Revise a specific existing ADR. Do not scaffold or silently change a decision's approval.

1. Confirm the absolute checkout root, read `adr/README.md`, `adr/template.md`, and the relevant numbered records in both layouts: `adr/NNNN-kebab-title/ADR.md` and legacy `adr/NNNN-kebab-title.md`. Resolve an explicit path or number first; otherwise require one unique title/topic match. If a number identifies multiple paths, several records could fit, or a directory has resources but no ADR.md, ask which record to use or how to recover it; do not create/replace one. If there is no matching file, offer `adr new` and stop. Reject paths outside the tracked `adr/` directory and never use `template.md` or a resource file as a target. Keep existing legacy ADRs at their current paths unless separately asked to migrate them.
2. Read the full existing ADR, its status, dates, options, links, and any history. Ask for the requested change when missing or vague. Distinguish new evidence, a clarification, a changed decision, and an explicit status transition. Preserve existing rationale, evidence, status, and history unless the user expressly revises them. A new decision that replaces a different ADR may need its own record and a supersession link; ask before making that transition. From a directory ADR, link to another directory ADR as `../NNNN-title/ADR.md` (or to a legacy file as `../NNNN-title.md`). From a legacy flat ADR, link to a directory ADR as `NNNN-title/ADR.md` (or to another legacy file as `NNNN-title.md`). Calculate the correct relative path from the _actual_ source and target files before editing. Never silently reset accepted to proposed, or claim approval from prose alone.
3. Make the smallest supported changes, retaining the document's existing MADR layout and any customized headings. Explain changed trade-offs with concise evidence and mark assumptions or unresolved questions. Keep existing diagrams and static resources beside `ADR.md`; check their relative links if changing them. When the decision or status materially changes, append a dated entry to `## Decision History` stating the previous and new status/outcome, why, and a link to evidence; preserve earlier entries verbatim. Update the main `Date` to the revision date without removing older dates from history. Clarifications that do not change the decision may leave history untouched. Do not replace the entire record with a new template.
4. If the summary or status changed, update only the matching row in `adr/README.md` to reflect the record. Keep the number and correct relative link (`NNNN-title/ADR.md` or legacy `NNNN-title.md`); preserve unrelated rows and index conventions. If its row is missing, duplicated, or points to a different record, ask before repairing the index. Check local links, including resources and cross-ADR references, and status agreement before reporting the exact paths touched. Do not commit or implement the ADR.

Example: “adr update 0004: the queue benchmark changes the chosen option; keep the earlier rationale” revises the existing file and adds a dated history entry. “adr update the storage decision” when several storage records exist requires a choice before editing anything.
